## P0 — Fix immediately

### P0-1. Corrupt base templates are one failed cron run from rendering
Program `bfea3f30` day_index 4-7 rows (`48e2b470`, `38463223`, `a0ce87e0`, `c8c92133`)
are byte-identical filler: `Deadlift 3x5@67%, Squat 3x5@63%, Bench 3x6@58%, Run 3.1mi`.
Date-pinned coverage ends 2026-08-02. Program is `num_cycles 13, days_per_week 7`, so
any date past coverage falls through to these rows.

**Corrected severity.** The cron is `0 5 * * 1` (Monday 05:00 UTC) and
`generate_weekly_program.py:520` computes `days_remaining = 6 - TODAY.weekday()`, so a
Monday run writes a full Mon-Sun block. The 2026-08-03 run extends coverage to 08-09
about an hour before 08-03 begins in MT. So this is **not a dated deadline** — it is a
zero-margin design:
- one failed or delayed Monday run exposes the filler on 4 of 7 days;
- browsing ahead in WeeklySchedule past the current week already shows the filler today;
- a `workflow_dispatch` on a Sunday computes `days_remaining = 0` and writes one day.

**Fix:** repair the four base rows regardless (they are wrong whenever they render);
make the generator keep a 2+ week buffer beyond `overrideMax` instead of stopping at the
week edge; refuse base-template fallback on a known-placeholder content hash.
**Zero-risk stopgap available now:** `workflow_dispatch` on `generate-weekly-program.yml`
with `days_ahead: 14` (the input is already wired to `DAYS_AHEAD` at line 516) buys two
weeks of margin without touching a row.

### P0-2. Service worker updates are blocked by a stale localStorage flag
`src/lib/workoutSessionFlag.js` sets `optigains-workout-active="1"`. It clears only on
complete/cancel, or when `checkForActiveSession` runs — which only happens when a workout
page mounts. `src/main.jsx:33-47` defers the SW `window.location.reload()` until that flag
is false. An abandoned session leaves the device pinned to an old JS bundle across every
subsequent deploy.
**This is the leading explanation for "fixes ship and I still hit the bug."**
**Fix:** clear the flag app-wide on startup for any `in_progress` session past a short
timeout, not just on workout routes.

### P0-3. `programs.cycle_length` does not exist — program create/update 400s
`src/pages/ProgramBuilder.jsx:444` writes `cycle_length` via `useProgramQueries.js:106`.
Verified against live `information_schema`: column absent, no migration ever adds it.
A prior audit's code fix shipped without its migration.
**Fix:** drop `cycle_length` from the payload (`days_per_week` already carries the value).

### P0-4. Cancel Enrollment has never worked
`useProgramQueries.js:447` writes `status: "cancelled"`. Live CHECK constraint is
`active | completed | paused`. Every cancel violates it.
**Fix:** write `completed`, or extend the constraint by migration.

## P1 — Programming correctness (why workouts don't match intent)

### P1-1. `set_delta` is computed and discarded — the engine never learns your real volume
`scripts/engine/deviation_tracker.py:159` returns `set_delta`. `generate_weekly_program.py`
never references it; `exercise_reward()` (`learners.py:230-233`) has no parameter for it.
You cut volume by hand every session and the engine re-prescribes the same load forever.
**This is the direct mechanism behind the Peters/Clark Kent override loop.**
**Fix:** thread `set_delta` into `exercise_reward()` as a negative term.

### P1-2. No anti-repeat guard on region selection
`session_generator.py:691-776` `_converge_split` hard-alternates the A/B variant but scores
region as pure `max(deficit_score x recovery_factor)`. A large deficit beats the 0.10
just-trained penalty, so the same region repeats. Produced 07-25 Lower B -> 07-26 Lower A
from one run.
**Fix:** hard penalty/exclusion on the previous day's region, mirroring the `last_strength`
check in the `_decide_split` fallback at line 815.

### P1-3. Polarized run plan is dead code — PST target has no lever
`allocator.py:282-299` `build_run_plan` computes 80/20 polarization, PST-gap scaling, and
`RUN_CONTINUOUS_CAP_MIN 45` / `RUN_INTERVAL_CAP_MIN 30`, writes to `weekly_plans.run_plan`,
and **nothing ever reads that column**. Actual cardio comes from `session_generator.py:569-638`
`pick_run_slot`/`_build_cardio`, called with hardcoded `max_quality=2, max_long=1` and
`_SLOT_SPEC` durations (long = 80 min) that ignore both caps.
Marked DONE under E13.
**Fix:** feed `pick_run_slot` from `plan["run_plan"]`/`pst_mult`/`vdot_gap`, or delete
`build_run_plan` and stop claiming the capability.

### P1-4. `focus` can never read "hypertrophy"
`generate_weekly_program.py:1378` hardcodes `focus` off the MPC action; the action set
(`mpc_prescriber.py:99-110`) has no HYPERTROPHY member. E1's hypertrophy weighting is real
and shapes set allocation via `allocator.py` — it just never reaches this column, which
means the column misreports engine intent.
**Fix:** derive `focus` from the dominant `goal_priorities` weight at write time.

### P1-5. The 19 -> 24 set jump was unintentional
Ruled out with certainty: NOT the 07-27 commits (they landed 20:02-21:06Z, after the 08:20Z
generation run that wrote the 24-set rows). No code change to `athlete_profile.py`/`allocator.py`
volume constants occurred in the 07-20 -> 07-27 window, so the increase is data-driven.
Best-supported cause, **consistent with but not verified**: `450bcd54` (07-23) fixed a bare
`"curl"` keyword miscrediting hamstring/leg/wrist curls to biceps; corrected attribution would
produce larger real deficits. The observed diff is +1 set each on Shrug, Bicep Curl, Face Pull,
Triceps OH Extension, Triceps Pushdown (exactly +5). Confirming the mechanism requires re-running
the allocator against historical logs — not done.
Correct fix per user decision: cap volume in cut mode (see P1-6), not revert the map fix.

### P1-6. NEW — cut mode / low-volume target (user decision 2026-07-30)
Current: 15 exercises / 24 sets on an Upper day. Peters upper/lower: ~6 exercises, 2 working
sets each. Clark Kent: 1-2 exercises per joint action, 1-2 sets, high frequency.
The engine has the right sets-per-exercise ratio and badly wrong exercise count.
**Fix:** add a cut/low-volume mode capping exercises-per-session and total sets, scaling with
deficit depth. This is a spec change to `Science-Unified.md`, not a bug fix.

### P1-7. Exploration hazard halt does not exist
`SCIENCE_ALIGNMENT.md` E8 and `Science-Unified.md:144` both claim exploration halts at
`hazard_score > 0.6`. `hazard` appears in zero Python files. Documented safety gate, never built.
**Fix:** implement a real gate off `guardrail.py` overreaching or Banister TSB, or correct both docs.

## P2 — Logging path reliability

- **Lost-update on enrollment progress.** `useProgramQueries.js:292-406` merges into a
  possibly-stale cached `enrollment` and blind-writes the whole object. Double-tap Finish or a
  second device silently erases a previously logged day. Fix: re-fetch inside `mutationFn`, or
  move the append into an atomic RPC.
- **`WeeklySchedule.jsx:162,164,225,353` uses browser-local `new Date()`** while `Today.jsx`
  uses `profile.timezone`. Same Today/Train disagreement class that `6b4d52ee` already fixed once.
  Fix: `nowInTz(profile?.timezone)`.
- **Approving a pending week doesn't invalidate the Today prescription.**
  `useProgramQueries.js:72-93` omits `queryKeys.todayPrescription`. Known gap in `6b4d52ee`,
  still open. Schedule updates, Today shows stale until next cron.
- **`workout_logs.program_id` / `enrollment_id` never written** on either save path
  (`WorkoutDetail.jsx:639-650`, `QuickWorkout.jsx:354-362`). All 142 rows null. Currently inert
  (no read site filters on them) — populate or drop.
- **Unordered fire-and-forget autosave.** `useWorkoutSession.js:90-100`, no debounce, no
  sequencing. Corrupts resume state only, not the final log. Fix: debounce + sequence number.
- **`programSchedule.js:24-42,190-206`** — `WEEKLY_OFFSETS`/`getDayOffset` documented to spread
  rest days, never called. `currentCycle`/`currentDayIndex` computed and unused; no pause/resume
  adjustment. Fix: wire it or delete it and correct the doc comment.
