# Known non-issues

Things that look like bugs to a fresh audit, get investigated, and turn out to
be fine. Check here before opening an investigation. If you find one of these
again, the finding is already closed — do not re-report it.

## The second `created_by` UUID in the data is a seeded test user

`5ec4eebf-ae62-4f3f-9c1d-f44f92716bc8` is **`athlete@local.test`**, the seeded
local dev athlete. It is not a second real account, not a data-corruption
artifact, and not a duplicate-write bug.

The live account is `169d2f0b-cf5a-44fb-8551-845004725a26`
(`nvtnachbar@gmail.com`).

What the test user actually is, verified against the live database:

- 56 `workout_logs` rows across 56 distinct dates, last one 2026-06-21.
- Every one of those 56 dates also exists on the live account, and the
  `exercises` jsonb is **byte-identical** on all 56 pairs (56 identical pairs,
  0 differing).
- **Zero** dates exist only on the test account. It contributes no history the
  live account doesn't already have.

Why it cannot affect anything:

- **Engine:** all three scripts read through an `sb_get` helper that injects
  `created_by=eq.USER_ID` into every query. See
  `scripts/compute_athlete_state.py:133-135`, `scripts/mpc_prescriber.py:158-159`,
  `scripts/generate_weekly_program.py:94-98`. The engine never sees these rows,
  so volume/fatigue totals do not double-count.
- **Frontend:** RLS is enabled with a policy on every user-scoped table, so the
  browser session cannot read them either.

### The `sb_get` trap

Grepping `sb_get(...)` **call sites** for `created_by` flags ~22 engine reads as
unscoped. They are not. The filter is injected by the helper definition, not
written at the call site. Read the helper before concluding a read is unscoped —
this false positive has been generated by more than one audit sweep.

### The one real duplicate

A single double-submit on the live account on **2026-06-22**. That one is
genuine. Everything else attributed to "duplicate logs" is the test user.

## Base-template rows repeating across day_index is the program, not corruption

`AUDIT_2026-07-30` P0-1 found four byte-identical filler rows in program
`bfea3f30`'s base template (`Deadlift 3x5@67%, Squat 3x5@63%, Bench 3x6@58%,
Run 3.1mi` at day_index 4-7). **That filler is gone — the template was repaired.**

What is there now, and will keep looking like a duplicate to a naive check:
`Strength + BUD/S Conditioning` is a 3-day rotation run twice in a 7-day cycle,
so day_index 1/4, 2/5 and 3/6 are byte-identical **by design**. A detector that
flags "same content on 3+ day indices" fires on every single week of this
program. `smoke.py` pins the actual filler signature instead, and separately
catches a template collapsed to one unique session.

## A session's UTC date is not its log date

`workout_sessions.start_time` is `timestamptz`; `workout_logs.log_date` is a
plain `date` in the athlete's local timezone (`America/Denver`). He trains in
the evening, so a session at `00:09Z` belongs to the **previous** local day.

Joining the two on the raw UTC date reports every evening workout as an
unlogged, lost session. This produced three false "lost workouts"
(2026-08-15, 08-21, 09-04) before the comparison was corrected — all three had
logs the whole time, on the local date. `smoke.py` resolves the timezone from
`user_profiles` before comparing.

## Schedule coverage below 14 days is not a P0-1 regression

The weekly cron writes roughly 14 days each Monday (`COVERAGE_BUFFER_DAYS = 7`
plus the days left in the week), then coverage decays a day at a time until the
next run. Mid-week it reads 12 days, Sunday 8. That is the design working.

The invariant that actually prevents P0-1 — the schedule running dry and the UI
falling back to a base template — is that a full week is always already written.
`smoke.py` asserts a 7-day floor with no gaps, not a fortnight.

## Ternaries and variable arguments in `db.entities.*` writes

Any static check that extracts written columns from `db.entities.X.create({...})`
must skip a ternary's `:` (`tag: cond ? e.timing : null` writes `tag`, not
`timing`) and must return nothing for a variable argument
(`update(id, updateFields)`), rather than scanning ahead to the next object
literal in the file. Both mistakes produce confident reports of nonexistent
columns — `food_entries.timing` and `program_enrollments.queryKey` were both
false positives from exactly this. The parser in `scripts/smoke.py` handles both.
